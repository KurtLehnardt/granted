Build story · agent-orchestrated

GRANTED
spec-driven, agent-built

A federal-funding tool built almost entirely by delegating to AI agents. The interesting part isn't the code. It's how much of a single 8-hour build we spent not writing any.

The premise

We didn't start with code. We started with a spec and a north star.

  • A north star for where the spec is silent: "a personal government-funding intelligence analyst for every startup." It governs every call the spec doesn't make.
  • An orchestrator contract (CLAUDE.md): one agent plans and delegates; it never writes code itself.
  • A 1,210-line specification (the orchestrator prompt): requirements, shared contracts, ship order, acceptance criteria.

Where the north star came from

The north star was built from a book: Architected Intelligence.

Jacob Miller & Jeremy Mumford · Principles for Building AI-First Organizations and Technologies. Five layers we mapped straight onto the product:

  • Output: anchor on the user's problem. Design around helping a founder secure funding, not around finding uses for AI.
  • Input: curate the "Canon." Turn messy government data into a trusted knowledge base that grounds the model.
  • Model: manage the triangle. Balance intelligence, cost, and latency; send expensive models only to the hard analysis.
  • Observability: measure trust with TACA. Transparency, Accuracy, Calibration, Alignment, checked with evals and expert vibe checks.
  • Enablement: focus on the build loop. Ship measurable value, watch real usage, iterate; skip the hype.

The operating model

Orchestrator → dispatcher → worker

        YOU (human) — prompts, approvals, course-corrections
            │
    ┌───────▼────────┐
    │  ORCHESTRATOR  │  decompose · plan · route · synthesize · MERGE centrally
    └───────┬────────┘
      ┌─────┴──────┐
      │ DISPATCHER │  (haiku — thin: relays the prompt, collects results)
      └─────┬──────┘
    ┌───────┴────────┐
    │     WORKER     │  (opus/sonnet — builds in an isolated git worktree)
    └────────────────┘

Cheap dispatchers, expensive workers. Many run in parallel; each gets a clean context. Only the orchestrator controls what reaches main.

Principle · define "done" before you delegate

How the work gets delegated

  • Recon before code. First produce an as-built map of the real pipeline, then confirm or kill every [HYPOTHESIS]. Never assign work to fix a problem you haven't proven exists.
  • Contracts first. Shared schemas, flags, and the prompt registry ship before any feature code, or parallel teams produce unmergeable work.
  • Every task is a sealed contract: Context · Files-in-scope · Definition-of-done · Out-of-scope · Test plan · Escalate-if. A task with no "out of scope" isn't ready to assign.
  • Route to specialist teams along a dependency graph: Contracts, Canon, Eligibility, Pipeline, Perf, Intel, Apply, Evals… each owning a file boundary so no two workers touch the same code.
  • Ambiguity is named, never guessed. Log it to open-questions.md, take the lowest-regret default, and record that default in the task.

Turn-based vs spec-driven · the shift

From conversation to specification.

how v1 was built · the hackathon MVP

a role + a conversation

No written spec. One operating contract ("you orchestrate, you delegate, you never implement yourself") plus a live stream of asks: "where's my loading bar," "add an auto-apply button," "divide and conquer, parallel teams." Improvised, one request at a time.

how v2 was built · the gap-closure buildout

a 1,210-line specification

The what and why pinned down in writing first: a problem statement, 11 requirements, 12 typed contracts, guardrails, teams, and acceptance criteria. Recon before code, then a human sign-off, then build.

Same operating rules both times. The difference: v1 discovered the product mid-conversation; v2 decided it on paper before anyone wrote code.

→ How the v2 spec was created

How it started

The project specs were used to create a starting prompt.

  • 1 v2 ran on a 1,210-line spec. A written, refined orchestrator prompt: R1–R10, 12 typed contracts, the Canon, guardrails, acceptance criteria. Every decision on paper before any agent ran.
  • 2 The gap-closure plan got the agent treatment. "Plan it as opus on xhigh": a plan for what v1 missed was drafted, critiqued by a separate opus/xhigh agent (which caught it citing the wrong branch), and refined until it met every criterion.

Principle · spend the time on the spec

Hours in — still not writing code.

We had a reasonable feature list: ask better questions, add a progress bar, competitor analysis, auto-apply. We could have started building any of them in the first ten minutes.

Instead we turned the list into a specification, then attacked the specification. Four rounds. Here's what that surfaced.

Principle · the spec surfaces the real problem

The ask was rarely the problem.

the progress bar

wasn't the problem

The search took three minutes. A beautiful bar over three minutes is still three minutes. The spec now requires you to measure where the time actually goes before changing anything. A guess about what's slow is usually wrong. A progress bar only makes the wait feel better. The real fixes were concrete: cache the full grant list and refresh it on a schedule, so a search never waits on government websites, and run the slow scoring steps at the same time. That took a typical search from three minutes to about 90 seconds.

"auto-apply"

became "assisted apply"

Submitting a federal application is a legally attested act. A human certifies it's true. A product that clicks submit for you doesn't save time, it transfers liability to you. So: prepare, prefill, review-and-attest. The human submits. Always.

The dividend · the spec grows and names its unknowns

The asks came with strings attached.

what we were asked for · the six
  • › Ask the smart questions before the search
  • › Resolve the "verify this" list for you
  • › Rewrite the company description
  • › Real progress, not a fake bar
  • › Competitor & market analysis
  • › Help me apply ("auto-apply")
what attacking the spec added · five more
  • › Make the slow search actually fast
  • › A real landing page + design system
  • › Check you're eligible, and it's still open
  • › Accounts, saved runs, billing
  • › Analytics + prompt version control

Each addition answered one question: what has to be true for the ask to actually work? A progress bar needs a fast search behind it. A match list is useless if you're not eligible. The paid features need accounts.

Principle · gates and flags are the guideposts

How dozens of agents didn't collide

  • Git worktree per task. Many agents edit the same repo without corrupting each other.
  • PR-per-task; the orchestrator merges centrally. One place controls ordering, conflicts, and main.
  • Six gates on every change: typecheck · test · build · hex · contrast · prompts. Green, or it doesn't merge.
  • Feature flags default-OFF. Every capability ships dark; the flag-off path stays byte-identical.
  • Verify the diff, not the report. Agents can over-claim; git is the source of truth.

The through-line

The hard part was never building faster.

It was being willing to cut the features that didn't deserve to exist. Once you've done that, ruthlessly, handing the actual work to a system that runs itself is the easy part.

Spec first. Delegate second. Automate merges behind review and quality gates. Put integrity in the code, not just the prompts.
