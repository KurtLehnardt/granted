Lightning talk · spec-driven development

Refine the spec.
Then let it run all night.

I built a real federal-funding tool by delegating to AI agents, writing almost none of the code by hand. The point isn't that agents wrote it. It's that once the spec was refined thoroughly, the orchestrator ran unattended, decomposing and delegating and merging, with no input from me. That autonomy is the payoff of spec-driven development.

What was in the 1,210 lines

Every decision, made up front.

  • Features, as 11 requirements. Each with a priority, a scope, and an explicit "out of scope."
  • A definition of done for every task. A testable checklist plus a test plan; nothing merges until it passes.
  • Instructions for the agents. Recon the real system first, confirm every assumption, delegate, gate every merge.
  • 12 typed data contracts. The shared schemas every agent builds against, locked before any feature code.
  • Guardrails. Cost ceilings, a privacy policy, and a list of non-goals we deliberately would not build.

Turn-based → spec-driven

From a conversation to a spec.

v1 · the hackathon MVP

a role + a conversation

One rule ("you delegate, you never implement yourself") plus a stream of asks: "where's my loading bar," "add an auto-apply button." Improvised, one prompt at a time.

v2 · the rebuild

a 1,210-line spec

The what and why in writing first: requirements, typed contracts, and a definition of done for every task. Recon before code, a human sign-off, then build.

Same agents both times. v1 discovered the product mid-conversation; v2 decided it on paper before anyone wrote code.

What the spec surfaced

Writing the spec surfaced unforeseen constraints.

behind "add a progress bar"

a 3-minute search

A prettier bar over three minutes is still three minutes. The real constraint was latency, not a missing bar. The spec forced the real fix: cache the data, run the scoring in parallel. 3 min → 90 sec.

behind "auto-apply"

a legal attestation

While auto-apply sounded ideal, submitting a federal grant means a human certifies it's true, under penalty. A bot can't take on that liability — so: prefill, review, the human submits.

The spec's guardrails

The guardrails caught the hallucinations.

automated · every change

six CI gates

Every PR must pass typecheck, tests, build, and three more before it can merge. A feature with no code fails its own tests. Red never merges.

agentic · every PR

review subagents in the loop

A dedicated code-review agent reads every pull request before the orchestrator merges it. Review is a step in the workflow, not a human afterthought.

Across 100+ PRs, every one had to clear the gates and a review. When an agent reported two features "done" with no code, the guardrails and review process caught it before it reached main. A hallucination that can't pass the tests and the review never ships.

Why it didn't need me

How it ran unattended.

  • Isolated by construction. A git worktree and a declared file boundary per task, so parallel agents never touch the same code.
  • Integration without a human. PR-per-task; the orchestrator merges centrally, only when the six CI gates are green.
  • Never block on the human. An open question gets a lowest-regret default and goes to a questions file. Nothing stops to wait for me. That is what let it run all night.

The one thing

Refine the spec until every decision is made. Then the orchestrator runs all night, no input needed.

Turn-based building keeps you in the loop for every step. A thorough spec takes you out of it: define "done," table the blockers, and let the swarm run.
